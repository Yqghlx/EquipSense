# 让 GLM-5.2 跑通工业告警全链路，6 分钟干完一天的活

最近在推一个工业设备监控平台 EquipSense（.NET 8 + React 19 + TimescaleDB + MQTT），赶上 6/13 GLM-5.2 全量上线 Coding Plan，把 Claude Code 底层模型切到 GLM-5.2 跑了几天，挑硬的说。

🚀 主线：让 GLM-5.2 用 6 分钟跑通告警全链路

给模型一句话任务：让模拟器生成真实工业数据，打通 模拟器→MQTT→后端→遥测入库→规则匹配→阈值评估→告警创建→聚合防风暴 全链路。

6 分 9 秒跑完，最后自己给了一张「故障验证矩阵」：

🔹 过载故障
　 触发：motor_current > 180A
　 阈值：180
　 告警码：ALT-AC-001-motor_current

🔹 润滑失效
　 触发：oil_temperature > 90°C
　 阈值：90
　 告警码：ALT-AC-001-oil_temperature

最有意思的是它自己规划了下一步：要做 AI 诊断评估仪表盘，对比 ground truth 和 analyses 表，量化命中率/误报率。模型不只是执行任务，还会主动规划产品演进。

🪲 顺手提一个让我印象深刻的 Debug

模拟器里"轴承磨损"剧本配置在 90 小时后触发，剧本 JSON 写的是 "at": "90:00:00"，跑了一晚上一次都没触发。打印 TimeSpan.TryParse("90:00:00") 输出 —— 返回的是 90 天，不是 90 小时。

C# 的 TryParse 有个超隐蔽行为：第一个数字 ≥24 时会按 d.hh:mm:ss 解析，把 90 当作天数。文档里写得小、搜索引擎搜不到、IDE 也不警告。

把现象丢给 GLM-5.2，一轮就给完整诊断 + 修复方案：换成 TimeSpan.TryParseExact 强制按"时:分:秒"解析。这个坑自己定位至少半天，模型 30 秒给根因。

⚠️ 真实说几个不足

不吹不黑：

📌 长上下文：项目有 2,400 行技术设计文档，整体能消化，但偶尔会忘前面定义的多租户约束，要主动提醒
📌 架构级权衡：让它设计分布式方案时，倾向给"现在能用"的方案，扩展性前瞻性不如顶级模型
📌 输出冗长：每次都附带验证代码+单元测试+设计点解释，简单问题被包装成大工程，token 消耗偏高
📌 偶尔自作主张：会主动跑没要求的额外任务（上面那个故障矩阵就是它自己加的），有时是惊喜有时是惊吓

但作为 Coding Plan 套餐能跑出来的国产模型，5.2 在 .NET 这种相对冷门的栈上表现已经相当能打。结构化输出能力尤其成熟，回答自带表格和分点，比一些海外模型还要规整。

📝 结论

GLM-5.2 在"端到端跑通一个完整任务"和"Debug 隐蔽坑"这两个场景里属于"省了我好几个小时"的级别。6 分钟跑通告警全链路 + 30 秒定位 .NET 时序解析坑，国产模型这几年的进步，确实有点超出预期。
