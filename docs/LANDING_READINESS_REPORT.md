> **SMTP 配置门禁增量（2026-08-14）**：邮件 worker 现在只在主机、1–65535 端口和有效发件人地址均满足时领取任务；非法配置会保留 Pending，不消耗重试次数。标准 `validate-env.sh` 与生产验收包均校验 SMTP 端口、发件人格式和 TLS 开关；生产验收对 SMTP 缺失或未启用 TLS 保持 `BLOCKED`，对非法端口和发件人格式返回 `FAIL`；新增 2 条 SMTP 服务回归、1 条环境门禁回归和 2 条验收契约回归。

> **MQTT 遥测可靠性增量（2026-08-14）**：发现边缘网关发布端虽然使用 QoS 1，但后端订阅端依赖 MQTTnet 默认值而实际请求 QoS 0，网络抖动期间可能静默丢失遥测；同时随机 ClientId + CleanSession 会让进程重启丢失未确认会话。后端现在以完全来自 `Mqtt__ClientIdPrefix` 的稳定 ClientId + 持久会话运行，不依赖容器机器名，在首次连接和断线重连时显式以 QoS 1 订阅，并新增订阅/会话回归测试；MQTT 客户端聚焦测试 7/7 通过。QoS 1 和持久会话仍不替代后端数据库持久化失败后的重试/告警，也不替代正式 Broker 重连、失败重投、积压恢复和端到端丢失率验收；当前真实生产 MQTT 外部证据仍为 `BLOCKED`。

> **遥测丢弃告警与 MQTT 交付增量（2026-08-14）**：数据库持续不可用且批量重试耗尽时，`TelemetryService` 会记录 `equipai_telemetry_dropped_total`；此前该指标没有对应的值班告警。现在新增 `TelemetryPersistenceDropped` Critical 规则（5 分钟窗口内出现增长即触发，持续 1 分钟确认），并补充运维手册的数据库、Outbox 与边缘网关积压排查路径。MQTT 消费路径等待所属批次完成持久化，失败时设置 MQTTnet `ProcessingFailed` 阻止 QoS ACK；同一消息内多指标并行等待，避免串行放大延迟。Shell 契约测试和 MQTT/遥测聚焦测试通过；Prometheus `promtool` 语义测试已纳入 CI，但当前开发机无 Docker daemon，需由 CI/有 Prometheus 工具链的环境执行最终规则语义验证。普通 HTTP 上报仍为异步 202，直接 HTTP 客户端需按响应和业务约定补发失败缺口。
