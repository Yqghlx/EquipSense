# 生产凭据初始化与整改门禁设计

> 日期：2026-08-13  
> 状态：按当前生产就绪改进目标进入实施准备  
> 范围：Docker 生产初始化脚本、生产只读自检、脚本契约测试和部署文档

## 背景

当前 `bash docker/validate-env.sh docker/.env --check-runtime-files` 能够正确阻断不安全配置，但工作区实测仍报告 27 项问题，包含缺失的本机随机凭据、重复环境变量、非 Production 环境、弱密码、HTTPS 主机名不匹配和证书有效期问题。仓库已有 `bootstrap-production-secrets.sh`，但操作路径需要用户手动记住多个脚本；同时，冲突重复键会直接终止初始化，失败后缺少按类别组织的下一步提示。

生产门禁必须继续 fail-closed。此次改进的目标不是让校验“变绿”，而是缩短从失败到正确修复的路径，并确保用户不会把隔离测试凭据、占位许可证或临时证书误带入生产。

## 目标

1. 为首次生产初始化提供一个明确的显式入口：用户可以选择在 `setup.sh` 中调用本机随机凭据补齐流程。
2. 只自动生成能够由本机安全随机源产生的字段；许可证、真实域名、SMTP/LLM/OTLP 凭据、TLS/MQTT 证书和真实租户配置仍必须人工或由密钥管理系统提供。
3. 保持重复键冲突、未知配置、弱凭据、非 Production、证书错误和外部依赖缺失的阻断语义。
4. 失败输出只包含键名、文件名、服务名和错误类别，不输出任何秘密值。
5. 对新模板、幂等重复执行、同值重复键修复、冲突重复键拒绝和秘密不泄露建立自动化契约。

## 非目标

- 不修改当前真实 `docker/.env`，不在测试或 CI 中写入仓库生产环境文件。
- 不自动生成或替换 TLS、MQTT、CA、许可证、域名、SMTP、LLM、OTLP 或对象存储配置。
- 不放宽 `validate-env.sh`、`production-readiness.sh` 或 Compose 的 fail-closed 规则。
- 不让脚本把“本机随机凭据已生成”报告为“生产可上线”。
- 不改变生产 Compose 的服务拓扑、数据库 Schema 或应用运行时业务逻辑。

## 方案比较

### 方案 A：在现有 `setup.sh` 增加显式 bootstrap 选项（采用）

增加 `setup.sh --bootstrap-local-secrets`，由它在环境文件准备后调用现有 `bootstrap-production-secrets.sh`；可选的 `--repair-identical-duplicates` 只允许归一化值完全相同的重复键，冲突值仍然失败。初始化完成后仍由 `setup.sh` 执行完整生产校验和运行时文件检查。

优点是复用现有的原子写入、随机源和校验逻辑，用户只需记住一个入口；默认不带选项时保持当前无副作用行为。代价是需要明确区分“生成本机凭据”和“外部生产配置仍缺失”两类结果。

### 方案 B：新建独立整改编排脚本

新增一个脚本负责调用 bootstrap、校验和打印报告，`setup.sh` 保持不变。优点是职责边界清晰；代价是新增入口和文档分叉，用户仍可能误用旧入口，且会重复编排现有脚本。

### 方案 C：只在 CI 增加模板契约检查

只验证 `.env.example` 与校验器字段一致，不改变本地部署体验。优点是实现成本低；代价是不能解决当前首次部署的操作断点，无法降低真实环境整改成本。

选择方案 A，因为它直接改善部署者体验，同时保持默认行为和安全边界不变。

## 设计

### 1. 初始化流程

`setup.sh` 解析以下选项：

- `--bootstrap-local-secrets`：在 `.env` 已存在或从模板创建后，调用 `bootstrap-production-secrets.sh --env-file <env>`。
- `--repair-identical-duplicates`：仅在同时启用 bootstrap 时向下传递；单独使用必须报参数错误，防止用户以为冲突值会被自动覆盖。

流程顺序固定为：

```text
检查脚本参数与路径
  → 创建/确认 .env 并收紧权限
  → （显式选择时）生成本机随机凭据 / 修复同值重复键
  → validate-env.sh <env> --check-runtime-files
  → 检查 Docker/Compose 和生产运行时文件
  → 只有全部门禁通过才允许继续生成 MQTT 密码文件或启动服务
```

bootstrap 失败时，`setup.sh` 立即停止，不继续创建密码文件或启动容器；bootstrap 成功但外部配置仍缺失时，setup 仍以非零状态退出，并明确列出需要人工完成的类别。

### 2. 整改输出

不改变现有错误的键名和文件名，只在脚本结束时增加脱敏的下一步提示：

- 本机可生成：建议运行 `--bootstrap-local-secrets`。
- 重复键冲突：要求人工确认并删除冲突定义，不自动选择最后一项。
- 许可证、域名、SMTP/LLM/OTLP、租户：提示由密钥管理系统或部署配置提供。
- TLS/MQTT 文件：提示预置正式证书并重新运行校验，不提供开发证书生成命令。
- Docker/Compose：提示安装或启动依赖，不把静态门禁失败隐藏在后续错误之后。

提示不得包含环境变量值、完整 URL 中的凭据部分、证书内容或脚本生成的随机值。

### 3. 模板与契约一致性

生产脚本测试增加静态契约：

- `validate-env.sh` 的必填环境变量都存在于 `.env.example`。
- `.env.example` 不包含重复键。
- bootstrap 可以在临时复制的模板上运行，生成本机字段但仍因外部许可证/证书缺失而失败。
- 重复执行 bootstrap 不改变已经生成的有效值。
- 同值重复键只有显式修复选项才会被归一化；冲突值永远不被自动覆盖。
- 测试输出不包含生成的随机值或环境变量敏感值。

测试使用临时目录和临时环境文件，不读取或修改工作区真实 `.env`。

### 4. 文档

更新 `docs/DEPLOY.md`、`docs/environment-variables.md` 和 `docs/OPS_RUNBOOK.md`：明确区分本机随机凭据、外部生产秘密、证书和最终上线验收；示例统一使用显式 bootstrap 选项，并保留“校验非零即禁止上线”的说明。

## 错误处理与安全边界

- 参数错误、路径符号链接、文件权限不安全、重复冲突、随机源失败和校验失败均返回非零。
- 原子临时文件和目录锁继续由 bootstrap 负责；任何失败都清理临时文件和锁目录。
- 不允许通过环境变量覆盖生产校验器路径或跳过外部证书检查。
- 生成值只写入权限为 600 的环境文件，不进入日志、命令行参数或测试断言输出。
- 生产环境仍需使用密钥管理系统注入并轮换秘密；脚本生成的本地值只是初始化辅助，不是密钥治理替代品。

## 验收标准

1. `bash -n docker/setup.sh docker/bootstrap-production-secrets.sh docker/validate-env.sh docker/production-readiness.sh` 通过。
2. 生产脚本契约测试覆盖上述模板、幂等、重复键和脱敏输出场景并通过。
3. 在临时模板上运行显式 bootstrap 后，本机可生成字段已存在且有效；外部配置缺失仍以非零退出。
4. `setup.sh` 不带新选项时保持原有行为，不自动修改现有有效凭据。
5. 后端/前端既有门禁不受影响，`git diff --check` 通过。
6. 文档明确说明：本地脚本绿灯不等于真实生产凭据、证书、SMTP、OTLP、现场协议和容量验收完成。
