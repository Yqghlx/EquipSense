# 告警规则评估资源边界设计

## 背景

`AlertEvaluationService` 在每条遥测到达时，将当前租户、指标和设备匹配的全部启用规则一次性读取到应用内存。规则数量较少时该实现简单，但规则规模增长后，会把单次遥测的内存占用和数据库返回量直接放大，成为告警热路径的无界资源风险。

## 目标

- 将规则读取改为数据库侧有上限的稳定游标分页。
- 每批最多读取 500 条规则，确保所有合法匹配规则仍会被评估。
- 保留既有租户、设备、设备类型和指标过滤条件。
- 保留当前规则顺序下的逐条评估、聚合、防重复、自动恢复和事件发布语义。
- 支持现有取消令牌在每批查询和规则处理中的传播。
- 对超过一批的 SQLite 真实查询增加资源边界回归测试。

## 非目标

- 不改变规则匹配条件、规则评估器、告警聚合策略或事件事务语义。
- 不在本次改动中引入规则缓存、并行评估或跨实例规则快照。
- 不修改生产凭据、部署配置或数据库迁移。

## 方案

使用 `AlertRule.Id` 作为稳定游标：基础查询按主键升序、`AsNoTracking()`，每次追加 `Id > lastRuleId` 和 `Take(500)`。批次内仍按现有顺序逐条执行完整评估；批次完成后推进游标，直到返回空批次或不足 500 条。

这种实现让数据库负责限制每次返回的行数，同时不通过 `Skip` 扫描前置页。规则实体仅用于读取和传入评估器，使用无跟踪查询不会影响告警实体的新增、更新和保存。

## 验收标准

1. 501 条匹配规则会产生至少两次规则查询，且每次规则查询均包含数据库侧 `LIMIT`。
2. 501 条规则全部传给匹配的评估器，不能因批次边界漏评估。
3. 现有告警单元测试、后端单元测试、集成测试和 Release 构建均通过。
4. 代码、测试和文档中的新增注释使用简体中文。
