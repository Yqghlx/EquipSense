# 知识规则冲突检测资源边界设计

## 背景

`KnowledgeConflictService.DetectConflictsAsync` 当前会把指定设备类型下全部启用知识规则一次性读取为实体投影，再在应用层解析条件 JSON。规则数量增长或用户频繁打开编辑表单时，单次请求的数据库返回量和应用内存占用没有固定上限。

## 目标

- 使用 `KnowledgeRule.Id` 升序稳定游标，每批最多读取 500 条规则。
- 保持当前租户、设备类型、启用状态和编辑排除自身的过滤语义。
- 让 501 条匹配规则全部参与冲突检测，不因分页边界漏报。
- 使用 `AsNoTracking`，因为规则只读并且不需要写回。
- 保持现有 `List<KnowledgeConflictResult>` 返回类型和完整冲突列表 API，不修改前端契约。
- 继续传播调用方取消令牌。

## 非目标与边界

- 不静默截断冲突结果；返回列表仍可能随真实冲突数量增长，这是当前 API 的业务输出本身。
- 不改造为分页冲突 API、不改变冲突 JSON 解析规则、不引入缓存或并行解析。
- 不修改真实凭据、部署环境或数据库 Schema。

## 方案

建立带既有过滤条件的 `IQueryable<KnowledgeRule>`，按主键排序。每轮根据上一个批次最后的 ID 追加 `Id > lastRuleId`，使用 `Take(500)` 查询只读投影；处理完当前批次后推进游标，直到批次为空或不足 500 条。

规则实体的读取内存被限制在单批 500 条，冲突结果列表仍完整累积并返回，确保用户看到的冲突不会因为资源保护而缺失。SQLite 回归测试将准备 501 条全部冲突的规则，验证结果数量、规则 ID 完整性、两次数据库查询及每次查询的 `LIMIT`。

## 验收标准

1. 501 条匹配规则返回 501 条冲突，且返回 ID 集合与种子 ID 集合完全一致。
2. 规则查询跨越两批，每条 `knowledge_rules` 查询均包含 `LIMIT`。
3. 现有冲突解析、租户隔离、排除自身和无匹配场景测试保持通过。
4. 后端单元测试、集成测试、Release 构建、生产脚本和差异检查通过。
