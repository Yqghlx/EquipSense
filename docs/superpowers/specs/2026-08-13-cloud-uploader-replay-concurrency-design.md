# 边缘网关离线回放并发安全设计

> 日期：2026-08-13  
> 状态：已确认，进入实施  
> 范围：`CloudUploader` 离线回放、MQTT 客户端创建和边缘网关单元测试

## 背景与根因

`Program.cs` 将 `CloudUploader` 注册为单例，但 `DeviceManager` 为每台设备启动独立的 `DataCollector`。每个采集器在线上传成功后都会调用 `ReplayOfflineDataAsync`。当前方法先从共享 SQLite 读取最多 100 条待发送记录，再逐条发布并标记；SQLite 的命令闸门只能保证单条读写不重叠，不能保护整个“读取—发布—标记”批次。两个采集器可能在第一批尚未标记前同时读取同一记录，造成重复 MQTT 发布。

## 目标与非目标

目标：

1. 在单进程单例 `CloudUploader` 内串行化完整的离线回放批次。
2. 等待回放锁时支持 `CancellationToken`，宿主停机不被永久阻塞。
3. 只在 MQTT 发布成功后标记记录已发送；发布失败、取消或断网时保留未发送记录。
4. 让测试能够注入 MQTT 客户端工厂，使用真实 `CloudUploader` 回放逻辑稳定验证并发行为。
5. 保持现有批量大小、SQLite Schema、QoS、指标和清理语义不变。

非目标：

- 不实现跨进程/多网关的 SQLite 消息租约；若未来一个数据库被多个进程共享，需要独立的 claim 状态设计。
- 不改变 MQTT 重连策略、断网入队策略或业务 API。
- 不把在线发布失败的当前消息和历史回放混为同一条记录。

## 设计

在 `CloudUploader` 增加实例级 `SemaphoreSlim _replayGate = new(1, 1)`。`ReplayOfflineDataAsync` 先检查取消，再执行 `WaitAsync(ct)`；获得锁后再次检查取消和在线状态，随后在 `try/finally` 内完成读取、逐条发布/标记和清理，最后释放闸门。`GetPendingAsync` 返回的记录在闸门持有期间完成整个发布批次，因此第二个采集器不会读到同一批未标记记录。

为测试增加可选 `Func<IMqttClient>` 工厂参数；生产构造函数默认仍使用 `MqttFactory.CreateMqttClient`，不改变调用方签名的既有参数顺序。测试使用可控的 `IMqttClient` 替身，在第一次发布暂停时并发调用第二次回放，断言第二次等待；释放后总发布次数等于记录数、每条记录只发布一次且 SQLite 无待发送记录。

## 错误与生命周期

- `OperationCanceledException` 原样传播，不写入离线存储，不把未完成消息标记为已发送。
- MQTT 发布异常由现有回放逻辑记录并停止当前批次；已成功发布且已标记的记录保持已发送，未处理记录留待下次回放。
- 任何异常或取消都通过 `finally` 释放闸门。
- `DisposeAsync` 在关闭 MQTT 客户端前取消/等待正在执行的回放不会由本次改动强行改变；闸门本身不提前释放，避免等待者在对象释放后进入共享客户端。
- 测试工厂只存在于可选构造依赖，不把 MQTT 凭据写入日志或断言。

## 验收标准

- 并发回放测试在旧实现下稳定失败，失败表现为第二次调用未等待或同一消息发布两次。
- 修复后并发回放测试通过，单回放、取消、发布失败和未连接既有测试继续通过。
- 边缘网关聚焦测试、后端全量单元、Release 构建和生产脚本门禁通过。
- 文档/风险登记明确该修复是单进程单例保护，不等同于多进程消息租约。
