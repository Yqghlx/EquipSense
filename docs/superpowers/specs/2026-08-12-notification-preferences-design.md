# 通知偏好真正生效设计

## 背景

设置页已经允许用户分别配置告警、工单、系统通知的 SignalR、浏览器推送和邮件开关，但现有通知分发链只保存这些配置，没有读取它们。结果是用户关闭实时通知或浏览器推送后，仍可能收到对应渠道的通知，形成错误的产品承诺。

## 目标与非目标

### 目标

- 站内通知继续按活动运维角色持久化，保证离线登录后仍能追溯历史。
- SignalR 即时通知按用户的通知类型偏好定向发送，并保持租户隔离。
- Web Push 只发送给开启对应类型 `push` 的用户，避免租户广播绕过偏好。
- 旧用户的空配置 `{}` 按默认值处理：SignalR/Push 开启，Email 关闭。
- 偏好过滤逻辑集中在应用层，后台任务和 HTTP 请求使用同一套规则。
- 没有收件人的通知不应报错、写入 `Guid.Empty` 记录或阻塞主业务。

### 非目标

- 本轮不实现告警/工单邮件通知。现有 SMTP 仅覆盖密码恢复；在邮件告警链、退订、重试和投递观测完成前，邮件开关保持不可用并明确告知用户。
- 不改变遥测数据广播和页面状态刷新语义；这些是实时数据功能，不是通知渠道。
- 不引入新的数据库表或迁移，继续复用 `users.notification_prefs` JSONB。

## 方案

### 1. 偏好解析与收件人筛选

扩展 `NotificationPreferenceService`，提供按租户、候选用户、通知类型和渠道筛选活动用户的能力。服务使用 `IgnoreQueryFilters` 配合显式 `tenant_id`，避免后台任务没有 HTTP 租户上下文时误查不到用户；解析失败回退到安全默认值（SignalR/Push 开启，Email 关闭）。

站内持久化只使用活动角色筛选，不读取渠道开关；这样用户关闭即时渠道后，登录通知中心仍能看到历史记录。

### 2. SignalR 定向组

`IndustrialHub` 连接建立时加入两类组：

- `tenant:{tenantId}`：遥测和页面状态刷新等非通知实时事件。
- `tenant:{tenantId}:user:{userId}`：需要尊重 SignalR 偏好的告警/工单通知。

服务端通过定向用户组发送通知，前端无需相信客户端传入的用户 ID。断开连接时移除两类组。用户组名称包含租户 ID，进一步降低跨租户组名碰撞风险。

### 3. Web Push 批量定向

扩展 `IPushNotificationService` 增加按用户 ID 集合批量发送的方法。实现一次查询租户内活动订阅，再按允许的用户集合过滤，复用现有失效订阅清理逻辑。SignalR 通知服务先按 `push` 偏好得到用户集合，再调用批量接口；不再对告警解除、SLA 升级和离线事件使用租户广播。

### 4. 邮件开关诚实降级

`NotificationPreferenceService.UpdateAsync` 将当前不支持的 Email 开关规范化为 `false`，并保留其 API 字段以兼容已有客户端。前端 Email 开关禁用并展示“暂不可用”说明；当未来邮件告警链完成后再移除该门禁。整行“全部开启”操作只作用于当前可用渠道，不会把不可用 Email 误标为开启。

## 错误处理与兼容性

- 偏好查询失败时，通知主流程不因偏好服务故障而丢失站内记录；SignalR/Push 采用独立降级并记录结构化警告。
- SignalR 普通网络异常继续隔离；宿主/请求取消继续传播。
- Push 无收件人时直接返回；单个订阅失败继续处理其他订阅，HTTP 410 继续清理。
- 空 JSON、旧字段和未知通知类型使用既有默认行为，不需要数据迁移。

## 测试策略

- 应用层单元测试：空配置默认值、关闭/开启每种可用渠道、Email 强制关闭、损坏 JSON 回退。
- SignalR 服务单元测试：只向偏好允许的用户组发送；Push 只收到允许用户集合；空收件人不调用外部通道；租户和活动状态过滤。
- Hub 单元测试：连接加入租户组和用户组，断开时清理。
- 集成测试：同租户两个用户互相不可见，跨租户用户不可见；通知中心仍能读取已持久化的历史通知。
- 前端测试：Email 开关禁用且有中英文说明；可用渠道切换和“全部”操作不覆盖不可用渠道。
- 生产验证：重新运行后端全量测试、前端类型/Lint/i18n/单测、Release 构建和 Production runtime smoke；完整 E2E 确认通知中心与实时告警流程不回归。

## 验收标准

1. 用户关闭告警 SignalR 后，不再收到告警实时事件；同租户其他开启用户仍能收到。
2. 用户关闭工单 Push 后，不收到工单 Push；其他允许用户仍可收到。
3. 关闭渠道不会删除或阻止站内历史记录。
4. 不同租户、停用用户和 `Guid.Empty` 均不会成为通知收件人。
5. Email 开关在 API 和 UI 中都不会表现为已实现功能。
6. 所有现有质量门禁保持通过。
