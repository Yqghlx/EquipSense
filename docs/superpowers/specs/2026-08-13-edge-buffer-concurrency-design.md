# 边缘网关断网缓冲并发安全设计

## 背景

边缘网关的每个设备采集器都可能并发调用上传管线。当前 `LocalBuffer` 使用
`ConcurrentQueue.Count`、`TryDequeue` 和 `Enqueue` 的多个独立操作实现容量控制；这些操作
虽然各自线程安全，但组合起来不是原子操作。在多个采集器同时断网时，队列可能短暂或持续
超过配置容量，造成内存不受控增长，且被驱逐消息可能并发写入同一个 `SqliteConnection`。

`SqliteBufferStore` 是单例，同时被 `LocalBuffer` 的溢出路径和 `CloudUploader` 的回放/清理路径
使用。现有实现没有串行化共享连接的生命周期和命令执行，真实断网恢复时可能出现连接并发访问、
回放失败或缓冲数据不完整。

## 目标

1. 在并发入队、出队和溢出持久化下，内存队列始终不超过 `BufferSize`。
2. 保持现有 FIFO 语义：内存队列保留较新的消息，被驱逐消息按驱逐顺序写入 SQLite。
3. 串行化共享 SQLite 连接的所有操作和释放，保留现有公开 API 与数据表结构。
4. 将队列深度指标同步到入队和出队后的实际快照，帮助运维识别积压和数据丢弃。
5. 对非法容量尽早失败，避免 `capacity <= 0` 导致入队死循环。

## 非目标

- 不改变 SQLite 7 天保留策略、回放批量大小、MQTT QoS 或上传重试策略。
- 不把内存队列改成无界队列，也不通过提高默认容量掩盖并发缺陷。
- 不改变 SQLite schema、配置键、构造函数签名或外部网关协议。
- 不在磁盘 I/O 期间持有内存队列锁；磁盘故障仍按现有语义计入 `BufferDroppedTotal`。

## 方案比较

### 方案 A：队列短锁 + SQLite 异步闸门（采用）

使用专用对象锁保护队列的检查、驱逐、入队、批量出队和深度指标快照；锁内只做内存操作。
被驱逐消息收集到局部列表后，在锁外逐条调用 SQLite。`SqliteBufferStore` 增加一个
`SemaphoreSlim`，所有共享连接操作都在闸门内完成，释放时也等待正在执行的命令结束。

优点是改动局部、保持现有 API、不会让采集线程等待 SQLite；缺点是多个溢出写入会在 SQLite
闸门处排队，磁盘极慢时仍会增加断网延迟，但不会破坏内存上限或连接状态。

### 方案 B：使用 `Channel<BufferEntry>` 替换队列

用有界 Channel 统一并发和异步背压。它能天然保证容量，但“驱逐最早消息并写入 SQLite”
需要额外消费者、取消和关闭协议，改变现有同步 `DequeueBatch` API，回归面更大，暂不采用。

### 方案 C：每次 SQLite 操作创建独立连接

避免共享连接竞争，但内存数据库测试、文件锁、连接生命周期和高频遥测写入成本更高；当前
边缘网关只需单实例串行访问，暂不引入连接池级复杂度。

## 详细设计

### LocalBuffer

- 构造函数要求 `capacity > 0`，否则抛出 `ArgumentOutOfRangeException`。
- 使用 `_queueLock` 保护 `_queue` 的组合操作。入队时在锁内循环驱逐直到有空间，再入队当前
  消息，捕获被驱逐项和深度快照；不在锁内等待 SQLite。
- 没有离线存储时，驱逐项计入 `BufferDroppedTotal`；有离线存储时逐项持久化，单项失败只
  计入丢弃指标并继续处理其它项，保持现有容错语义。
- `DequeueBatch` 在锁内批量取出并更新 `BufferQueueDepth`；`FlushToOfflineStoreAsync` 复用批量出队，
  `DisposeAsync` 清空后将深度指标置零；宿主仍单独释放 SQLite 单例。

### SqliteBufferStore

- 增加 `_operationGate` 和 `_disposed` 状态；`InitializeAsync`、`StoreAsync`、`GetPendingAsync`、
  `MarkAsSentAsync`、`CleanupOldAsync`、测试辅助方法和 `DisposeAsync` 都必须经过同一闸门。
- 闸门只保护 SQLite 连接和命令；不把网关队列锁传入存储层，避免锁顺序反转。
- `DisposeAsync` 先取得闸门，再标记释放、关闭并释放连接，最后释放闸门；已经释放或正在释放
  的 store 拒绝新的操作，避免后台回放访问已关闭连接。
- 命令和 reader 在闸门内及时释放；查询结果在释放闸门前完整物化，调用方不会持有数据库游标。

### 指标和错误处理

- 队列深度指标是锁内快照，不输出主题或载荷内容。
- SQLite 写入失败不把异常传播到采集循环，继续使用现有 `BufferDroppedTotal` 计数；回放和
  清理的异常传播策略保持不变，由上层记录并在下次周期重试。
- 任何取消、MQTT 或协议行为不因本设计改变。

## 验证策略

新增/调整单元测试覆盖：

1. `capacity` 为零和负数时构造失败。
2. 多任务并发入队后，`Count` 永不超过容量，且保留消息数量等于容量。
3. 并发溢出写入 SQLite 后，所有成功持久化的消息可完整查询，不出现连接并发异常。
4. 出队和清空后队列深度指标分别反映实际数量和零值。
5. 现有存取、排序、回放、清理、磁盘故障计数和释放测试继续通过。

## 发布边界

本改动只影响边缘网关进程内的并发和本地缓冲可靠性；仍需要在真实 PLC/OPC UA/Modbus、
断网超过 7 天、磁盘耗尽、MQTT 恢复和正式容量预算下进行部署侧验收。
