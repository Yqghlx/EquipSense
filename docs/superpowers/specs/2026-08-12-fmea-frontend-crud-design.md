# FMEA 前端 CRUD 设计

## 背景与目标

FMEA 后端已经提供按租户隔离的新建、详情、更新、删除和启停接口，前端也已有新建/更新 hooks，但 FMEA 页面只支持查询、启停和删除。现场人员无法在产品内维护故障模式库，导致知识沉淀仍需绕过系统完成。

本次只补齐 FMEA 页面内的新建与编辑闭环，目标是让有知识库写权限的用户能够安全、可理解地维护 FMEA 条目，同时不改变租户边界和现有只读角色体验；前后端均遵循项目既定的“维保主管知识库 RW+验证”权限矩阵。

## 方案与边界

采用独立 `FmeaFormDialog` 组件承载表单，`FmeaPage` 仅负责列表数据、权限判断和弹窗开关状态。弹窗接收 `open`、当前 `entry` 和 `onOpenChange`，`entry` 为 `null` 表示新建，非空表示编辑；组件内部复用现有 `useCreateFmeaEntry` 与 `useUpdateFmeaEntry` hooks。

不新增第三方依赖，不新增后端 FMEA 端点，不把 FMEA 改成多步向导，也不在本轮引入规则选择器。`knowledgeRuleId` 保留为可选文本字段，服务端只允许当前租户或系统租户规则，前端同步做 GUID 格式校验；后续若需要可单独设计知识规则搜索交互。

## 交互设计

### 页面入口

- 页面标题右侧显示“新建 FMEA”，仅 `perm.canCreate` 为真时渲染。
- 每行操作区在启停按钮旁显示编辑按钮，仅 `perm.canEdit` 为真时渲染。
- 新建或编辑成功后关闭弹窗，并依赖 hooks 的 `['fmea']` 查询失效机制刷新列表。
- 关闭弹窗时清空未提交草稿，避免跨条目泄漏上一次输入。

### 表单布局

弹窗使用现有 shadcn/ui Dialog，最大高度限制为视口的 90%，内容可滚动。视觉上沿用工业监控页面的 slate 基础色，以风险评分作为唯一强调点：

- “故障识别”区域：设备类型、故障模式、故障原因、故障影响、检测方式、建议措施。
- “风险评分”区域：严重度 S、发生频率 O、可检测性 D，三个输入并排展示，均限制为 1–10 的整数。
- 风险评分区域旁实时显示 `RPN = S × O × D`。风险色阶与列表保持一致：`>=200` 红色、`>=100` 橙色、其余黄色；输入不完整时显示占位符而不是误导性数值。
- “关联规则”区域：可选 `knowledgeRuleId` 文本输入。
- 底部提供取消和保存按钮；保存按钮在请求期间禁用并显示加载文案。

这组布局把长文本和数值风险分开，减少现场录入时的认知切换；RPN 预览是该表单的识别性元素，直接告诉用户三项评分会如何影响风险排序。

## 校验与错误处理

- 文本字段提交前 `trim()`，六个文本字段均必填；前端错误提示使用已有的字段级双语文案。
- 三个评分字段必须是 1–10 的整数；空值、非整数、越界均显示对应错误，且通过 `aria-invalid` 与 `aria-describedby` 关联 `role="alert"` 提示。
- `knowledgeRuleId` 为空时不发送该字段；非空时保留用户输入并去除首尾空白。
- 文本字段长度和 GUID 格式与后端 DTO 保持一致；服务端最终校验关联规则的租户归属。
- 发送请求前清除旧错误；请求失败时保留草稿，在弹窗内显示可理解的通用失败提示，允许用户修改后重试。
- 成功回调关闭弹窗；关闭或取消不会调用 mutation。

## 测试策略

- 组件测试覆盖：新建默认值、编辑回填、提交请求字段、RPN 预览、空值/越界校验、无障碍错误关联、失败后保留草稿、成功关闭。
- 页面测试覆盖：有权限时显示新建入口与行编辑入口，无编辑权限时不显示写操作；点击入口能够打开对应模式。
- 执行 `npm run check:i18n` 确保中英文键集合一致，并执行 TypeScript、ESLint、Vitest 和生产构建门禁。

## 成功标准

1. 维保主管或系统管理员可在 FMEA 页面新建并编辑完整条目，保存后列表显示新的 RPN。
2. 只读角色看不到新建、编辑、删除等写操作入口，现有启停/删除权限行为不被改变。
3. 表单在键盘和屏幕阅读器场景下能定位字段错误，失败不会清空用户已经填写的内容。
4. 前端门禁全部通过，且不引入新的 lint warning 或中英文 i18n 缺口。
