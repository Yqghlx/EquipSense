# WAF 规则受控热更新设计

## 背景

当前 `WafMiddleware` 将 SQL 注入、路径遍历、命令注入和 XSS 检测规则静态编译在代码中。静态规则执行效率稳定，但生产环境无法在不发布后端镜像的情况下补充新的攻击特征；直接接受任意运行时正则又可能引入 ReDoS、误配导致全站不可用或通过规则覆盖削弱基线防护。

本设计只解决“可审计、可回滚、可热加载地补充规则”这一生产运维缺口，不引入数据库管理 API，也不把租户业务配置与 WAF 规则混在一起。

## 目标与非目标

### 目标

1. 生产启动时验证规则文件，文件缺失、权限不安全、JSON 格式错误或规则不安全时拒绝启动；规则文件为非敏感配置，需允许镜像内非 root 应用用户读取，但禁止组/其他用户写入。
2. 运行期间监听规则目录；通过临时文件写入后原子替换正式文件即可触发热加载，无需重启后端。
3. 规则加载采用不可变快照。有效新版本原子切换，已有请求继续使用其取得的快照；无效新版本保留上一版，避免一次错误更新造成全站失去 WAF 防护。
4. 保留代码内置的四类安全基线，外部文件只能增加受限规则，不能关闭或覆盖基线规则。
5. 对规则文件记录版本、SHA-256、规则数量和加载结果，日志中不打印规则正文，便于审计和故障排查。
6. 为规则文件提供明确的挂载路径、权限要求、更新步骤和回滚证据。

### 非目标

- 不提供面向浏览器或普通租户管理员的 WAF 管理 API。
- 不支持从数据库、远程 URL 或未经认证的网络请求拉取规则。
- 不允许外部文件替换内置规则或提交任意可执行代码。
- SHA-256 只用于批次完整性和审计标识，不声称提供签名认证；规则目录的最小权限、只读挂载、发布审批和制品来源仍由部署系统负责。

## 方案选择

### 方案 A：受限本地规则文件热加载（采用）

后端从只读挂载目录读取版本化 JSON。文件中的规则使用固定字段和受限匹配类型：`contains` 进行不区分大小写的字面量匹配，`regex` 使用 `.NET RegexOptions.NonBacktracking`、长度上限和超时。内置基线始终启用，外部规则只能追加。文件通过目录监听和原子替换触发 reload。

优点是无新增网络攻击面、无数据库依赖、可在多副本部署中由同一制品系统分发，并且失败时可以保留上一版。代价是规则变更需要运维发布文件制品，不能由业务用户在线编辑。

### 方案 B：数据库规则管理 API

可提供系统管理员 API、版本记录和审计界面。动态性更高，但会把高风险规则编辑能力暴露到业务服务，必须额外处理 RBAC、跨租户边界、并发发布、缓存一致性和数据库不可用时的启动策略，本阶段不采用。

### 方案 C：完全交给外部 WAF

由云 WAF 或反向代理维护攻击规则，应用只保留输入校验。该方案适合边缘防护，但不能替代应用内部安全边界，也不覆盖本地、隔离网和现场边缘部署，本阶段不采用。

## 详细设计

### 1. 规则模型

规则文件格式固定为：

```json
{
  "schemaVersion": 1,
  "revision": "2026-08-13.1",
  "rules": [
    {
      "id": "custom-sqli-load-function",
      "category": "sql-injection",
      "matchType": "contains",
      "pattern": "load_file",
      "description": "拦截新增的数据库文件读取函数特征"
    }
  ]
}
```

约束如下：

- `schemaVersion` 只能为 `1`；`revision` 为 1～64 个可打印 ASCII 字符，用于审计和回滚识别。
- `rules` 最多 128 条；`id` 只能包含小写字母、数字、点、短横线和下划线，长度 1～64，且不得重复或与内置规则 ID 冲突。
- `category` 只能是 `sql-injection`、`path-traversal`、`command-injection`、`xss`。
- `matchType=contains` 的 `pattern` 是非空字面量，最多 256 个 Unicode 字符；匹配使用 `OrdinalIgnoreCase`。
- `matchType=regex` 的 `pattern` 最多 256 个字符，禁止反向引用、条件表达式、回溯控制、lookaround 等不受支持或难以审计的构造；编译使用 `IgnoreCase | CultureInvariant | NonBacktracking`，执行超时为 50ms。
- `description` 最多 256 个字符，禁止控制字符；日志只记录 `id`、`category`、`revision` 和摘要，不记录 `pattern`。
- 规则文件最大 64KiB，必须是普通文件，不能是符号链接；生产环境下路径必须为绝对路径，文件及其父目录不得对组或其他用户可写。

内置四类规则继续由代码编译并自动加入每个快照。外部文件只提供追加规则，因此错误或恶意更新不会关闭现有基线。

### 2. 加载与热更新

新增单例 `IWafRuleProvider`，职责仅包括当前快照、首次加载和规则文件 reload；新增纯函数式 loader 负责读取、解析、校验、编译和计算 SHA-256。快照中的规则集合使用只读数组，发布时通过 `Interlocked.Exchange` 原子替换，WAF 请求路径不持有全局锁。

生产配置使用 `Security:Waf:RulesPath=/etc/equipai/waf/rules.json` 和 `RequireExternalRules=true`。规则目录以只读方式挂载到后端容器。开发/单测可不提供外部文件，此时使用内置基线，避免开发体验依赖生产挂载。

监听规则目录而不是单个文件，以兼容 `rules.json.tmp` 写完后 `mv` 替换 inode 的原子发布方式。文件系统事件使用约 250ms 防抖；reload 失败仅记录错误并保留上一版。首次加载失败直接抛出配置异常，使生产进程在监听端口前失败。

有效 reload 日志包含：`revision`、规则数量、SHA-256、加载耗时和结果；失败日志包含失败类别与文件路径，不包含规则正文、密钥或请求体。

### 3. WAF 请求路径

`WafMiddleware` 改为从 `IWafRuleProvider.Current` 取得快照，并交给独立 matcher 检查 URL/query/body。保留现有 `IsMalicious(string)` 内部兼容入口，使现有静态单测仍能锁定内置基线；新增 provider 注入测试验证外部规则命中、快照切换和无效 reload 保留旧快照。

命中日志增加 `RuleId` 和 `Category`，仍只记录客户端 IP、路径和来源位置，不记录完整 URL、query、body 或规则正文，降低敏感数据泄露和日志爆炸风险。

### 4. 容器与运维

- 新增受版本控制的 `docker/waf-rules/rules.json` 基线扩展文件，并在 base/production/smoke Compose 中以目录只读挂载到 `/etc/equipai/waf`。
- 生产更新流程为：在临时路径生成新文件 → 运行结构和规则安全校验 → 计算 SHA-256 → 备份当前文件 → 原子 `mv` 到 `rules.json` → 检查后端日志和 WAF 规则快照指标；失败时将备份文件原子恢复。
- 应用不接受远程拉取或 HTTP 修改；更新权限由部署账户和文件系统控制。
- 在运维手册中记录规则 revision、SHA-256、发布人/流水线、开始结束时间、reload 结果和回滚结果，禁止记录规则正文中的敏感样例。

## 错误处理与安全边界

| 场景 | 行为 |
|------|------|
| 生产规则文件缺失 | 启动失败，不监听业务端口 |
| 首次 JSON/权限/规则校验失败 | 启动失败并报告变量名/路径/错误类别 |
| 运行中更新文件非法 | 保留上一有效快照，记录错误并暴露失败计数 |
| 运行中更新文件有效 | 原子切换快照，已有请求不受阻塞 |
| 外部规则与内置 ID 重复 | 拒绝整个新版本，保留上一版 |
| 正则包含不安全构造或编译超时 | 拒绝整个新版本，保留上一版 |
| 规则文件权限变为组/其他可写或变为符号链接 | 拒绝整个新版本，保留上一版 |

## 测试与验收

1. loader 单测覆盖：完整合法文件、空规则、重复 ID、非法版本、非法分类、超长字段、控制字符、未知字段、符号链接、危险权限、超大文件、非法 regex、NonBacktracking 兼容性和摘要稳定性。
2. provider 单测覆盖：首次加载、开发缺省基线、生产缺失失败、有效文件热更新、非法更新保留旧快照、连续文件系统事件防抖、并发读取无异常。
3. WAF middleware 单测覆盖：内置基线仍命中、外部 contains/regex 规则命中、正常输入放行、命中日志只含规则 ID/分类、不含 body/query/规则正文。
4. 生产脚本契约测试覆盖：Compose 只读目录挂载、Production 必须启用外部规则、smoke 使用当前规则文件、文档包含原子替换和回滚步骤。
5. 运行 `dotnet test tests/EquipAI.Tests.Unit`、`dotnet build EquipAI.sln -c Release`、`bash tests/scripts/production-scripts-test.sh all` 和现有 Production runtime smoke；不得修改真实 `docker/.env`。

## 发布与回滚判定

只有在内置基线单测、外部规则 loader/provider 测试、生产脚本契约、Release 构建和 Production runtime smoke 均通过后，才将合规报告中的 WAF 规则更新项标记为“代码已实现”。正式生产仍须由部署方完成规则制品审批、最小权限和一次有效更新/回滚演练；这不能被仓库测试替代。
