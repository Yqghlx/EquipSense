# MFA 恢复码运营验收设计

## 背景

EquipSense 已经实现一次性 MFA 恢复码：只在生成响应中返回明文，数据库保存 SHA-256 摘要；登录消费和重新生成共享用户级分布式锁，并写入审计事件。当前缺口不是重新设计算法，而是缺少一条跨 HTTP 管线的可复现证据，证明实际接口和运维验收所依赖的安全边界没有被中间件、数据库或错误处理破坏。

## 目标与非目标

目标：

1. 通过集成测试验证恢复码登录成功后立即失效，重复使用返回未授权。
2. 通过集成测试验证重新生成要求当前 TOTP，旧恢复码全部失效，新恢复码可用。
3. 验证消费、重新生成成功和失败都留下正确的审计动作，审计描述不包含恢复码明文。
4. 验证恢复码锁无法获得时请求安全失败，不修改恢复码摘要。
5. 把自动化证据、人工演练边界和“禁止在正式生产测试中消耗恢复码”写入运维文档。

非目标：

- 不修改恢复码格式、哈希算法、API 路径或响应结构。
- 不在生产数据库、正式账号或正式恢复码上运行自动化测试。
- 不把恢复码明文写入日志、测试报告、快照或提交内容。
- 不把集成测试替代生产现场对密钥管理、密码管理器和恢复流程的人工演练。

## 设计

### 测试分层

- `MfaRecoveryCodeServiceTests` 继续负责纯函数边界：生成数量、格式、大小写/分隔符归一化、损坏摘要拒绝和消费后剩余摘要。
- `AuthServiceTests` 增补审计载荷、错误路径和锁拒绝测试；测试替身记录动作、租户、资源和描述，但永不记录候选恢复码。
- `AuthControllerTests` 增补完整 HTTP 流程：登录取得 MFA challenge → 使用恢复码验证 → 重复使用失败 → 使用 Bearer 会话以当前 TOTP 重新生成 → 旧码失败、新码成功。测试用户使用随机用户名、测试租户和测试密钥，测试结束清理用户和审计记录。
- 并发安全采用可控的测试分布式锁替身：同一用户的恢复码锁只允许一个请求进入，第二个请求必须收到未授权并且不写数据库；不使用真实生产 Redis 或真实恢复码。

### 审计契约

以下动作必须保持稳定：

| 场景 | Action | ResourceType | 允许的描述内容 |
|---|---|---|---|
| 恢复码登录成功 | `AuthMfaRecoveryCodeUsed` | `User` | 用户标识和事件结果，不包含恢复码 |
| 恢复码重新生成成功 | `MfaRecoveryCodesRegenerated` | `User` | 旧码失效和生成结果，不包含恢复码 |
| TOTP 错误 | `MfaRecoveryCodesRegenerateFailed` | `User` | 验证失败原因，不包含 TOTP 或恢复码 |

审计记录的 `TenantId` 和 `ResourceId` 必须对应当前用户，不接受请求体中的租户字段覆盖；测试通过数据库查询验证这一点。

### 错误和数据安全

- 恢复码无效、已消费或锁争用统一走现有 `401` 认证失败语义，不泄露“某个码是否曾经有效”的额外信息。
- 重新生成失败不能改变现有摘要；成功保存新摘要后才返回新码。
- 任何测试断言只比较状态、数量、摘要可消费性和审计动作；不会把明文恢复码输出到控制台或失败消息。

## 验收标准

- 集成测试证明单个恢复码只能完成一次 MFA 登录。
- 集成测试证明重新生成后旧码不可用、新码可用且返回 8 个码。
- 单元/集成测试证明审计事件按租户写入，描述中不含任一测试恢复码或 TOTP。
- 锁拒绝测试证明恢复码摘要保持不变。
- 运维手册明确：正式验收需使用专用账号、离线保存恢复码、验证单次消费和重新生成；自动化测试不得消费正式恢复码。
- 相关后端单元、集成测试、Release 构建和生产脚本门禁全部通过。
