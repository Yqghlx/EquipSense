## 三、错误处理模式

### 后端三层结构

```
Layer 1: 全局异常中间件 (ExceptionHandlingMiddleware)
    └── 未捕获异常 → 统一 JSON { code, message, details }
        ├── UnauthorizedAccessException → 401
        ├── KeyNotFoundException → 404
        ├── InvalidOperationException → 409 (含状态流转非法)
        ├── ArgumentException → 400
        └── 其他 → 500 (记录 Error 日志)

Layer 2: 业务层 try-catch 60+ 处
    ├── LogWarning(4xx) — 客户端错误（配置缺失、降级、外部失败）
    ├── LogError(5xx) — 服务端错误（DB 不可用、LLM 超时）
    └── 降级回退:
        ├── LLM 不可用 → 通用经验诊断 (置信度 0.3)
        ├── 后端 API 不可达 → 本地 appsettings.json fallback
        ├── MQTT 上传失败 → 离线缓冲 (LocalBuffer + SQLite)
        └── 审计记录失败 → catch { LogWarning } 绝不阻塞业务

Layer 3: 前端 Axios 拦截器 (api.ts)
    ├── 无响应 → "网络连接失败"/"请求超时"/"无法连接服务器"
    ├── 403 → "您没有权限执行此操作"
    ├── 404 → "请求的资源不存在"
    ├── 429 → "操作过于频繁，请稍后再试"
    ├── 500 → "服务器内部错误，请稍后重试"
    └── 502/503/504 → "服务暂时不可用，可能正在维护或过载"
```

### 反模式审查结果

| 反模式 | 计数 | 位置 | 是否可接受 |
|--------|------|------|-----------|
| `async void` | **0** | — | ✅ |
| `.Wait()` / `.Result` | **3** | InMemoryEventBus 停机等待 (1) + TelemetryService 同步 flush 兜底 (2) | ✅ 全部有界且仅用于停机/资源释放路径；正常宿主优先使用异步释放 |
| `GetAwaiter().GetResult()` | **0** | — | ✅ 已移除；异步释放优先走 `DisposeAsync` |
| 空 `catch { }` | **4** | EdgeGateway Dispose/Close 路径 | ✅ 资源清理场景可接受 |
| 异常信息暴露给用户 | **0** | 全部通过 JSON 响应包装 | ✅ |
| TODO/FIXME/HACK | **0** | — | ✅ |
| `pragma warning disable` | **2** (手动代码) | OpcUaAdapter CS0618 (废弃 API) | ✅ SDK 版本兼容 |

### 最佳 — `AlertEvaluationService.cs` 的完整场景覆盖

```csharp
// 覆盖了 5 种边界场景:
// 1. 正常触发告警
// 2. 防风暴 (第2-3次更新) 
// 3. 防风暴 (>3次静默)
// 4. 震荡指标 (shouldUpdate但无Active告警 → 兜底创建)
// 5. 重启后防重复 (DB查重 → 降级为更新)
```

### 停机路径同步兜底 — `TelemetryService.Dispose`

`TelemetryService` 已提供真正的 `DisposeAsync`，宿主优先通过异步释放等待最后一次 flush。同步 `Dispose` 仅作为不支持异步释放的宿主兜底，并对获取 flush 闸门和执行 flush 分别设置 10 秒上限；超时后记录告警并交由边缘网关的离线缓存重传，避免数据库不可达时无限阻塞容器关闭。该路径仍属于生命周期级同步等待，但不再是业务请求路径，也不使用无界的 `GetAwaiter().GetResult()`。
