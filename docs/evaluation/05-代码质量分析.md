## 三、错误处理模式

### 后端三层结构

```
Layer 1: 全局异常中间件 (ExceptionHandlingMiddleware)
    └── 未捕获异常 → 统一 JSON { code, message, details }
        ├── UnauthorizedAccessException → 401
        ├── KeyNotFoundException → 404
        ├── InvalidOperationException → 409 (含状态流转非法)
        ├── ArgumentException → 400
        └── 其他 → 500 (记录 Error 日志)

Layer 2: 业务层 try-catch 60+ 处
    ├── LogWarning(4xx) — 客户端错误（配置缺失、降级、外部失败）
    ├── LogError(5xx) — 服务端错误（DB 不可用、LLM 超时）
    └── 降级回退:
        ├── LLM 不可用 → 通用经验诊断 (置信度 0.3)
        ├── 后端 API 不可达 → 本地 appsettings.json fallback
        ├── MQTT 上传失败 → 离线缓冲 (LocalBuffer + SQLite)
        └── 审计记录失败 → catch { LogWarning } 绝不阻塞业务

Layer 3: 前端 Axios 拦截器 (api.ts)
    ├── 无响应 → "网络连接失败"/"请求超时"/"无法连接服务器"
    ├── 403 → "您没有权限执行此操作"
    ├── 404 → "请求的资源不存在"
    ├── 429 → "操作过于频繁，请稍后再试"
    ├── 500 → "服务器内部错误，请稍后重试"
    └── 502/503/504 → "服务暂时不可用，可能正在维护或过载"
```

### 反模式审查结果

| 反模式 | 计数 | 位置 | 是否可接受 |
|--------|------|------|-----------|
| `async void` | **0** | — | ✅ |
| `.Wait()` / `.Result` | **3** | Program.cs 停机回调 (2) + TelemetryService 同步 flush (1) | ⚠️ 停机路径可接受，flush 路径待修复 |
| `GetAwaiter().GetResult()` | **1** | TelemetryService.cs:329 | ⚠️ 建议改为真正的异步 |
| 空 `catch { }` | **4** | EdgeGateway Dispose/Close 路径 | ✅ 资源清理场景可接受 |
| 异常信息暴露给用户 | **0** | 全部通过 JSON 响应包装 | ✅ |
| TODO/FIXME/HACK | **0** | — | ✅ |
| `pragma warning disable` | **2** (手动代码) | OpcUaAdapter CS0618 (废弃 API) | ✅ SDK 版本兼容 |
