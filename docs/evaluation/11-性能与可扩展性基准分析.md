# EquipSense 性能与可扩展性基准分析报告

> 分析日期：2026-07-02（数据校正） · 范围：遥测管线 · 告警引擎 · 后台服务 · 前端渲染

---

## 一、遥测数据管线吞吐分析

### 1.1 完整链路

```
边缘网关 MQTT → Mosquitto Broker → MqttBackgroundService
  → MqttMessageHandler (JSON 解析)
  → TelemetryService.EnqueueAsync (批量写入队列, 1000 条 / 500ms 刷入)
  → AppDbContext.BulkInsert → device_telemetry (TimescaleDB)
  → TelemetryReceivedEvent → InMemoryEventBus (Channel, 10000 条容量，满载背压)
  → TelemetryEventHandler (设备状态更新 + 告警评估)
```

### 1.2 瓶颈分析

| 节点 | 容量 | 瓶颈 | 建议 |
|------|------|------|------|
| MQTT 接收 | 无限制 | 单线程处理 | 可并行消费 |
| TelemetryService 队列 | 1000 条/500ms | 突发超过 2000/s 时可能积压 | 可调参 |
| InMemoryEventBus（开发/应急路径） | 10000 条 Channel, Wait + 5 秒发布超时 | 满载时发布端背压；持续消费停滞时单条事件会超时丢弃并记录错误 | 生产默认使用 RabbitMQ；监控发布超时和 RabbitMQ Outbox 指标 |
| EF Core Write | Npgsql 连接池 | 200 max_connections | 当前充裕 |
| 告警评估 | 同步阻塞 | 多规则拖慢吞吐 | 告警评估可选异步 |

**关键风险**：`InMemoryEventBus` 仅用于开发、测试和显式授权的生产应急降级。当前 Channel 容量为 10000，满载时采用 `Wait` 背压而不是静默 `DropOldest`；如果消费者持续停滞超过 5 秒，发布端会记录错误并丢弃当前事件。因此生产环境必须保持 RabbitMQ Provider，并监控 Outbox 发布确认、重试和失败指标。

### 1.3 ThreadPool 调优

```csharp
// Program.cs: 容器环境默认线程数=CPU核心(2-4)
// 遇到突发并发时，新线程1个/秒缓慢启动 → 请求堆积
// 预设50个worker/IOCP防止ThreadPool饥饿
ThreadPool.SetMinThreads(workerThreads: 50, completionPortThreads: 50);
```

## 四、后台服务资源消耗

| 服务 | 周期 | 每次 DB 查询 | 内存消耗 | CPU |
|------|------|-------------|---------|-----|
| BusinessMetricsCollector | 30s | 4 次固定聚合/计数查询（alerts/work_orders/knowledge/pending_rules） | 固定标签摘要 | 低 |
| DeviceStatusMonitor | 30s | 超时设备按 500 条主键分页；每批更新并通知 | 有界 | 中 |
| GatewayHeartbeatMonitor | 30s | 超时网关按 500 条主键分页；每批更新并通知 | 有界 | 中 |
| BaselineCalculationService | 周期 | 按设备聚合 | 中 | 中 |
| TelemetryCleanupService | 每天 3:00 | 活跃租户按 500 条主键分页后逐租户 DELETE | 有界 | 中 |
| SlaEscalationHostedService | 5min | 活动工单按 500 条主键分页；每批升级并提交 | 有界 | 中 |
| DeviceHealthRecalculationHostedService | 10min | 设备按 500 条分页；每批告警聚合、遥测限量 | 有界 | 中 |

**多实例风险（历史评估）**：10 个后台服务此前缺分布式锁；当前已由 `LockedTimerService` 统一接入 Redis 分布式锁，并在长任务期间按 token 续租，续租失败取消本轮任务。容量压测仍需覆盖多实例 Redis 故障场景。

## 七、本轮性能复核补充（2026-08-14）

本轮使用 SQLite 关系型测试上下文的 `DbCommandInterceptor` 锁定了多个高频分析读路径的数据库往返与资源上限，并通过后端单元测试验证：

| 路径 | 原实现 | 当前实现 | 回归证据 |
|------|--------|----------|----------|
| 设备详情最新遥测 | 先聚合最新时间，再按指标逐条查值（1+N） | 单次按指标分组、按时间取最新值 | `TelemetryQueryServiceTests`：3 个指标固定 1 次 SELECT |
| 设备详情历史遥测 | 未限制时间范围和返回行数，可能把高频设备海量数据加载到应用内存 | 时间范围最多 7 天，数据库侧限制最近 10000 个点，非法范围在 HTTP 层返回 400 | `TelemetryQueryServiceTests` / `TelemetryControllerTests`：范围拒绝与 `LIMIT` 回归 |
| 设备横向对比 | 设备列表后逐设备读取窗口遥测（1+N） | 设备列表、窗口聚合、最新值批量读取固定 3 次 SELECT，应用内仅保留设备级摘要 | `DeviceComparisonServiceTests`：3 台设备固定 3 次 SELECT，并验证最新值按时间确定、聚合 SQL 存在 |
| 批量趋势预警 | 每个设备+指标分别查询遥测和阈值（1+2N），并把 7 天原始点加载到内存 | 7 天按设备/指标/小时聚合，阈值按活动设备指标集合聚合；结果按设备/指标排序后流式处理，保留原始样本计数，应用层只保留当前小时序列 | `TrendAnalysisServiceTests` / `TrendBatchResourceBoundaryTests`：聚合 SQL、排序和固定 2 次 SELECT 回归 |
| 租户设备健康度重算 | 每台设备最多 4 次 SELECT + 1 次保存，设备数增长导致往返和事务线性增长；近期告警逐条加载；活跃租户 ID 一次性加载 | 活跃租户 ID 与设备均按 500 条稳定排序分页；每批告警按设备/严重级别/状态数据库聚合，遥测每设备最多 100 条，批次独立保存并清理跟踪器 | `DeviceHealthRecalculationHostedServiceTests`：501 租户 `LIMIT`、固定小批次 3 次 SELECT、告警 `GROUP BY`、good/bad/无遥测分数 |
| 单设备数据质量评估 | 最近 1 小时原始遥测无上限加载，高频设备可能造成内存峰值 | 完整性使用数据库 `COUNT`；统计维度最多加载最近 10000 条，报告保留完整样本计数 | `DataQualityBackgroundScopeTests`：10005 条样本验证 `LIMIT` 与完整计数 |
| 运营报表 | 设备、告警和工单原始实体按窗口全部加载，366 天窗口可能造成内存峰值 | 设备/告警/工单统计和告警指标分布由数据库聚合，健康度排名只读取最低 10 台 | `OperationsReportResourceBoundaryTests`：设备/告警/工单 SQL 验证 `GROUP BY` 与有限排名 |
| 仪表盘与 OEE | 活跃告警、工单状态和 7 天趋势先读取原始行再在内存分组，OEE 读取全部设备状态 | 设备、状态分布和 OEE 设备比例由数据库计数；趋势按租户本地日期的 UTC 半开边界计数，应用层只保留固定桶 | `DashboardStatsResourceBoundaryTests`：仪表盘与 OEE SQL 均验证 `COUNT`；既有时区统计回归保持通过 |
| 知识规则导出 | JSON/CSV 导出无条数上限，规则规模增长会把所有实体加载到应用内存 | 两种格式共享稳定排序和 10000 条数据库 `LIMIT` | `KnowledgeImportServiceTests`：10001 条规则验证两种格式均只返回 10000 条 |
| 审批待办查询 | 当前租户待审批记录一次性加载，再在应用层兼容历史角色格式；大租户待办规模增长可能造成请求内存峰值 | 显式租户/状态/指定审批人过滤，按 `WorkOrderApproval.Id` 稳定游标每批最多 500 条，`AsNoTracking` + 最小投影；批次内规范化角色，最终按步骤顺序返回完整结果 | `ApprovalPendingResourceBoundaryTests`：501 条待办验证两次 `LIMIT` 查询、跨批角色规范化和完整 ID 集合 |
| 工单统计 | 统计周期内先加载全部工单，再在应用层计算分布、趋势、完成时长和 SLA | 状态/类型/优先级、租户本地日期趋势、完成时长和 SLA 均在数据库侧聚合；PostgreSQL 完成时长使用 `EXTRACT(EPOCH)`，应用层只接收有限摘要 | `WorkOrderStatisticsResourceBoundaryTests`：SQLite 验证全部工单 SELECT 均含 `GROUP BY`，并校验完成时长/SLA 结果 |
| 业务指标采集 | 每 30 秒把全部活跃告警和工单原始行加载到应用层再分组，数据量增长会持续放大后台内存 | 活跃告警按严重级别、工单按状态由数据库计数，知识规则和待审核规则保持固定聚合/计数查询；停机取消令牌贯穿查询 | `BusinessMetricsCollectorResourceBoundaryTests`：SQLite 验证告警/工单 SELECT 均含 `GROUP BY` |
| SLA 扫描与概览 | 每 5 分钟租户 ID 与活动工单均一次性加载，规模增长会放大内存、跟踪器和长事务 | 租户 ID 与活动工单均按稳定主键分页，每批最多 500 条；工单批次独立提交/清理跟踪器；概览先按优先级/状态数据库聚合，再用固定 `COUNT` 查询按 SLA 时间边界拆分 | `SlaEscalationHostedServiceTests` / `SlaManagementResourceBoundaryTests`：501 租户和 501 工单均验证 `LIMIT`，概览验证 `GROUP BY` |
| 设备/网关状态监控 | 每 30 秒一次性加载全部超时设备或网关，规模增长会放大后台内存和通知批次 | 两条路径均按 UUID 稳定分页，每批最多 500 个候选；状态更新仍复核时间戳防竞态，通知查询限制在当前批次；停机取消在通知失败时继续传播 | `StatusMonitorResourceBoundaryTests`：设备/网关各 501 条验证 `LIMIT`，并验证通知取消传播 |
| 订阅到期处理 | 试用与订阅到期租户实体一次性加载并由 EF 跟踪，租户规模增长可能造成内存峰值和长事务 | 两类到期租户均按 UUID 稳定分页，每批最多 500 条；状态/套餐/配额由数据库侧批量条件更新，保留租户级日志 | `SubscriptionExpiryResourceBoundaryTests`：两类各 501 个租户验证读取均含 `LIMIT`，并校验降级/过期状态 |
| 遥测保留清理 | 活跃租户保留策略一次性加载，租户规模增长会放大内存；随后逐租户删除 | 活跃租户按 UUID 稳定分页，每批最多 500 个，仅保留当前批次配置；逐租户删除语义和停机取消不变 | `TelemetryCleanupServiceTests`：501 租户验证租户读取均含 `LIMIT`，取消回归保持通过 |

这组回归不替代真实 PostgreSQL/TimescaleDB 的 `EXPLAIN (ANALYZE, BUFFERS)` 和容量压测，但能防止代码重构重新引入随设备/指标数量线性增长的数据库往返或无界内存加载。健康度批处理中的遥测相关子查询按设备限制最近 100 条，数据质量评估按指标限制最近 10000 条，避免定时任务和诊断链路把历史时序数据全部加载到应用内存。

## 八、可扩展性瓶颈

| 瓶颈 | 影响 | 解决方案 |
|------|------|---------|
| InMemoryEventBus（10000 + Wait） | 应急路径持续停滞时可能发生发布超时丢单 | 生产保持 RabbitMQ；为发布超时、Outbox 重试/失败配置告警 |
| 后台服务锁租约失效 | 长任务可能重复 | Redis token 条件续租；续租失败取消本轮任务 |
| TelemetryService 单队列 | 积压 | 多分区队列 |
| 全表扫描后台服务 | 大数据量慢 | 游标 + 分页 |
| 同步告警评估 | 阻塞遥测处理 | 异步评估 |
| EF Core N+1 (已部分修复) | 串行 DB 查询 | Task.WhenAll 并行 |
