# EquipSense 性能与可扩展性基准分析报告

> 分析日期：2026-06-24 · 范围：遥测管线 · 告警引擎 · 后台服务 · 前端渲染

## 一、遥测数据管线吞吐分析

### 1.1 完整链路

```
边缘网关 MQTT → Mosquitto Broker → MqttBackgroundService
  → MqttMessageHandler (JSON 解析)
  → TelemetryService.EnqueueAsync (批量写入队列, 1000 条 / 500ms 刷入)
  → AppDbContext.BulkInsert → device_telemetry (TimescaleDB)
  → TelemetryReceivedEvent → InMemoryEventBus (Channel, 1000 条容量)
  → TelemetryEventHandler (设备状态更新 + 告警评估)
```

### 1.2 瓶颈分析

| 节点 | 容量 | 瓶颈 | 建议 |
|------|------|------|------|
| MQTT 接收 | 无限制 | 单线程处理 | 可并行消费 |
| TelemetryService 队列 | 1000 条/500ms | 突发超过 2000/s 时可能积压 | 可调参 |
| InMemoryEventBus | 1000 条 Channel, DropOldest | **容量太小** — 突发遥测峰值可能丢事件 | 建议扩容到 10000+ |
| EF Core Write | Npgsql 连接池 | 200 max_connections | 当前充裕 |
| 告警评估 | 同步阻塞 | 多规则拖慢吞吐 | 告警评估可选异步 |

**关键风险**：`InMemoryEventBus` Channel 容量 1000，如果 TelemetryEventHandler 处理慢于遥测到达率，Channel 满 → DropOldest → 事件丢失。

### 1.3 ThreadPool 调优

```csharp
// Program.cs: 容器环境默认线程数=CPU核心(2-4)
// 遇到突发并发时，新线程1个/秒缓慢启动 → 请求堆积
// 预设50个worker/IOCP防止ThreadPool饥饿
ThreadPool.SetMinThreads(workerThreads: 50, completionPortThreads: 50);
```

## 二、告警引擎性能

### 2.1 告警评估耗时

```csharp
// 通过 Prometheus Histogram 监控:
// buckets: 1, 2, 4, 8, 16, 32, 64, 128, 256, 512 ms
BusinessMetrics.AlertEvaluationDuration
```

**典型场景延迟估算**：

| 评估器 | 单次耗时 | 说明 |
|--------|---------|------|
| ThresholdEvaluator | < 1ms | 简单比较 |
| BaselineEvaluator | < 2ms | 含 DB 基线查询 |
| CombinedEvaluator | < 5ms | 多条件评估 |
| 全链路 (含事件发布) | 10-50ms | 含 Channel 写入 |

### 2.2 防风暴保护

```csharp
// 30分钟窗口:
// 第1次 → 创建
// 第2-3次 → 更新
// >3次 → 静默
// 每10分钟清理过期窗口
```

**峰值隔离**：进程内内存态，重启后窗口重置（有 DB 兜底防重复告警）。

## 四、后台服务资源消耗

| 服务 | 周期 | 每次 DB 查询 | 内存消耗 | CPU |
|------|------|-------------|---------|-----|
| BusinessMetricsCollector | 30s | 3 次全表扫描 (alerts/work_orders/knowledge) | 低 | 中 |
| DeviceStatusMonitor | 30s | 1 次全表扫描 (超时设备) | 低 | 低 |
| GatewayHeartbeatMonitor | 30s | 1 次全表扫描 (超时网关) | 低 | 低 |
| BaselineCalculationService | 周期 | 按设备聚合 | 中 | 中 |
| TelemetryCleanupService | 每天 3:00 | 按租户逐条 DELETE | 高 | 高 |
| SlaEscalationHostedService | 5min | 全表扫描逾期工单 | 中 | 中 |
| DeviceHealthRecalculationHostedService | 10min | 全表扫描设备 + 遥测 | 高 | 高 |

**多实例风险**：10 个后台服务缺分布式锁 → 多实例时重复执行且 DB 负载翻倍。

## 五、前端性能

### 5.1 Bundle 大小

```
main bundle:     266 KB    (首屏)
echarts chunk:   1.1 MB    (独立加载, 按需)
react-vendor:    218 KB
signalr chunk:    54 KB
form-vendor:      93 KB
```

### 5.2 缓存策略

```typescript
// TanStack Query
staleTime: 5 min       // 5 分钟内不重请求
gcTime: 10 min         // 10 分钟后回收未用缓存
refetchOnWindowFocus: false  // 不自动刷新

// SignalR 是唯一失效触发器
// 后端推送事件 → invalidateQueries → 自动刷新
```

### 5.3 分包策略

```typescript
// vite.config.ts manualChunks
if (id.includes('echarts')) return 'echarts'
if (id.includes('react-dom')) return 'react-vendor'
if (id.includes('@microsoft/signalr')) return 'signalr'
if (id.includes('react-hook-form') || id.includes('zod')) return 'form-vendor'
```

## 七、可扩展性瓶颈

| 瓶颈 | 影响 | 解决方案 |
|------|------|---------|
| InMemoryEventBus (1000) | 丢事件 | 扩容 + 迁移 RabbitMQ |
| 后台服务无分布式锁 | 多实例重复 | RedLock |
| TelemetryService 单队列 | 积压 | 多分区队列 |
| 全表扫描后台服务 | 大数据量慢 | 游标 + 分页 |
| 同步告警评估 | 阻塞遥测处理 | 异步评估 |
| EF Core N+1 (已部分修复) | 串行 DB 查询 | Task.WhenAll 并行 |
