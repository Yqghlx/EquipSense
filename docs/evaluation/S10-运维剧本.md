## 场景 1: 后端容器反复重启

**症状**：`docker ps` 显示 backend 容器状态 `restarting`

**排查步骤**：

```
1. 查启动日志
   docker compose logs backend --tail=100

2. 常见启动失败原因对照
   ┌──────────────────────────┬─────────────────────────────────┐
   │ 日志关键词               │ 问题                           │
   ├──────────────────────────┼─────────────────────────────────┤
   │ JWT 密钥不安全           │ JWT_SECRET 未配或长度不足 32    │
   │ CORS 配置缺失            │ 生产环境未设 FRONTEND_URL       │
   │ PostgreSQL 连接失败      │ PG_PASSWORD 错误 / PG 未就绪    │
   │ Redis 连接失败           │ REDIS_PASSWORD 错误 / Redis 未就绪│
   │ Address already in use   │ BACKEND_PORT 被占用             │
   └──────────────────────────┴─────────────────────────────────┘

3. 验证环境变量
   docker compose config  # 检查 .env 加载是否正确
   
4. 检查依赖服务健康
   docker compose ps     # postgres/redis/mosquitto 是否 healthy
```

**解决**：

```bash
# 修复 .env 中的 PG_PASSWORD / JWT_SECRET
# 确保依赖服务先就绪
docker compose up -d postgres redis mosquitto
sleep 10
docker compose up -d backend
```

## 场景 2: 告警不推送（运维收不到通知）

**症状**：设备遥测异常触发了告警，但站内通知/钉钉/飞书均无反应

**排查链路**：

```
MQTT 收到 → 告警评估 → 创建告警 → 事件总线 → Handler → 通知分发

Step 1: 确认告警已创建
  后端日志: grep "告警已创建" | grep "ALERT"
  API: GET /api/v1/alerts?status=active
  
Step 2: 确认 SignalR 推送
  后端日志: grep "SendAsync" | grep "OnAlertTriggered"
  → 无日志 → 可能是 AlertEventHandler 被过滤器吞掉 (历史问题见 C01，commit `59a3752`+`2755d2a` 已修复)
  
Step 3: 确认通知配置
  API: GET /api/v1/tenants/{id} → 检查 Settings.integrations
  必需字段: webhookUrl (非空, 非 undefined)
  
Step 4: 确认 MQTT 连接
  指标: equipai_mqtt_connected == 1
  探针: GET /health/ready → mqtt: Healthy
```

**常见原因**：

| 原因 | 排查 | 修复 |
|------|------|------|
| 后台过滤器吞掉 Handler | 后端日志无 AlertEventHandler 输出 | 已修复 (commit `59a3752`) |
| Webhook URL 反序列化 null | 检查 Settings JSON 的大小写 | 统一 camelCase |
| 告警级别 < Critical | 钉钉/飞书只推送 Critical/High | 确认告警级别 |
| MQTT 断连 | `equipai_mqtt_connected == 0` | 检查 Mosquitto 状态 |

## 场景 3: 磁盘空间满

**症状**：`df -h` 显示使用率 > 90%，PostgreSQL 可能拒绝写入

**排查步骤**：

```bash
# 1. 查看磁盘使用分布
df -h
du -sh /var/lib/docker/volumes/*  # Docker 数据卷大小
du -sh /var/log/*                   # 系统日志

# 2. 查看容器日志占用
docker ps -q | xargs docker inspect --format='{{.LogPath}}' | xargs du -sh

# 3. 查看 PG 数据大小
docker exec equipai-postgres psql -U postgres -d equipai \
  -c "SELECT pg_size_pretty(pg_database_size('equipai'));"

# 4. 查看各表大小
docker exec equipai-postgres psql -U postgres -d equipai \
  -c "SELECT relname, pg_size_pretty(pg_relation_size(relid)) FROM pg_stat_user_tables ORDER BY pg_relation_size(relid) DESC;"

# 5. 检查备份目录
ls -lh docker/backups/
```

**常见增长源**：

| 数据源 | 增长速率 | 自动清理 | 手动清理 |
|--------|---------|---------|---------|
| device_telemetry | ~1GB/天/100 设备 | TimescaleDB 压缩+保留 365天 | 降低保留天数 |
| audit_logs | ~50MB/天 | LogRetentionCleanupService 365天 | `DELETE FROM audit_logs WHERE created_at < now() - interval '180 days'` |
| notifications | ~20MB/天 | LogRetentionCleanupService 90天 | `DELETE FROM notifications WHERE created_at < now() - interval '30 days'` |
| Docker 容器日志 | ~100MB/天/容器 | 无 | `docker compose logs --tail=0` 或限制 `max-size` |
| 备份文件 | ~500MB/次 | backup.sh 保留 7 天 | `find backups \( -name "*.dump" -o -name "*.sql.gz" \) -mtime +7 -delete` |

**解决**：

```bash
# 限制容器日志
echo '{"log-driver":"json-file","log-opts":{"max-size":"10m","max-file":"3"}}' > /etc/docker/daemon.json
systemctl restart docker

# 手动清理备份
find docker/backups \( -name "*.dump" -o -name "*.sql.gz" \) -mtime +7 -delete

# 强制清理超期遥测 (紧急)
docker exec equipai-postgres psql -U postgres -d equipai \
  -c "DELETE FROM device_telemetry WHERE time < now() - interval '90 days';"
```

## 场景 4: 遥测数据延迟 / 仪表盘不更新

**症状**：设备在线但仪表盘数据不再变化，或数据显示延迟 > 1 分钟

**排查链路**：

```
边缘网关 → MQTT Broker → 后端接收 → 入库 → 事件 → 告警 → SignalR → 前端

Step 1: 检查边缘网关
  curl -H "X-Gateway-Auth-Key: $GATEWAY_AUTH_KEY" http://edgegateway:8081/status
  → collections_total 是否在增长？
  → upload_fail_total 是否 > 0？
  → buffer_queue_depth 是否 > 0？
  
Step 2: 检查 MQTT Broker
  docker logs equipai-mosquitto --tail=50
  → 是否有连接/断连记录？
  
Step 3: 检查后端 MQTT 接收
  指标: equipai_mqtt_messages_received_total 是否在增长？
  日志: grep "MQTT" | tail -20
  
Step 4: 检查 TelemetryService
  指标: equipai_telemetry_received_total (tenant_id, device_id)
  → 如果 metrics 有接收但前端不更新 → SignalR 问题
  
Step 5: 检查前端 SignalR
  前端: RealtimeIndicator 是否绿色？
  如果灰色 → 连接断开 → 刷新页面或检查网络
```

**指标**：

```bash
# 实时监控遥测流入
curl -s http://localhost:8080/metrics | grep equipai_telemetry
```

## 场景 5: 升级回滚

**症状**：新版本部署后出现稳定性问题，需回退到上一版本

**操作步骤**：

```bash
# 1. 确认当前和上一版本的 SHA
docker images | grep equipsense/backend

# 2. 回滚后端
docker compose stop backend
docker compose -f docker-compose.yml run --rm backend \
  -e TAG=<前一版本SHA>  # 或用 docker tag 重新标记 latest
docker compose up -d backend

# 3. 验证回滚
docker compose logs backend --tail=20
curl http://localhost:8080/health  # 确认 Healthy

# 4. 回滚前端 (如有必要)
docker compose stop frontend
docker compose -f docker-compose.yml run --rm frontend \
  -e TAG=<前一版本SHA>
docker compose up -d frontend
```

**注意事项**：
- 数据库迁移不可回滚！如需回滚，请从备份恢复数据库
- 回滚前后端分别操作，先后端再前端
- 如果数据库迁移已执行且不可逆，回滚后可能不兼容。此时只能 forward-fix。

## 场景 6: 数据库迁移失败

**症状**：`dotnet ef database update` 报错，或应用启动时迁移失败

**常见原因**：

| 错误 | 原因 | 解决 |
|------|------|------|
| `already exists` | 迁移已部分执行 | `dotnet ef database update <上一迁移名称>` |
| `column xxx of type jsonb does not exist` | 迁移顺序问题 | 检查迁移依赖 |
| `Cannot drop index` | 索引被其他对象依赖 | 先检查依赖再删除 |
| `Permission denied` | PG 用户权限不够 | `GRANT ALL ON DATABASE equipai TO postgres;` |

**安全操作流程**：

```bash
# 1. 先备份
docker exec equipai-postgres pg_dump -U postgres -d equipai > pre_migration_backup.sql

# 2. 查看待执行的迁移
dotnet ef migrations list --project src/EquipAI.Infrastructure --startup-project src/EquipAI.WebAPI

# 3. 生成 SQL 脚本审查 (推荐!)
dotnet ef migrations script --project src/EquipAI.Infrastructure --startup-project src/EquipAI.WebAPI \
  --output migration_review.sql
# 审查 migration_review.sql 后再执行

# 4. 执行迁移
dotnet ef database update --project src/EquipAI.Infrastructure --startup-project src/EquipAI.WebAPI
```

## 场景 7: 边缘网关离线

**症状**：网关看板中某网关显示 offline，该网关下所有设备数据均不更新

**排查步骤**：

```bash
# 1. 检查网关进程是否在运行
docker ps | grep edgegateway
curl http://edgegateway:8081/health

# 2. 检查网关日志
docker logs equipai-edgegateway --tail=50
# 搜索: "MQTT 已连接"、"采集异常"、"重连"

# 3. 检查后端网关记录
curl http://localhost:8080/api/v1/gateways
# 确认 last_heartbeat_at 是否为最近时间

# 4. 检查网络连通性 (从网关容器)
docker exec equipai-edgegateway ping mosquitto
docker exec equipai-edgegateway curl http://backend:8080/health

# 5. 检查 AuthKey 是否匹配
# .env 中的 GATEWAY_AUTH_KEY 必须与后端配置一致
```

**常见原因**：

| 原因 | 排查 | 修复 |
|------|------|------|
| AuthKey 不匹配 | 后端日志 401 | 统一 .env 中的 GATEWAY_AUTH_KEY |
| 网络不通 | ping 失败 | 检查 Docker 网络 `docker network ls` |
| MQTT 认证失败 | 网关日志 "Connection refused" | 检查 MQTT 用户名密码 |
| 证书过期 | 网关日志 "certificate expired" | 重新生成证书 |
| 配置拉取失败 | 网关日志 "配置刷新失败" | 检查 BackendUrl 配置 |
| 初始设备配置为空 | 网关日志 "已加载 0 个设备" | 检查 appsettings.json 或后端 API |
| 长期离线后 SQLite 满 7 天 | 数据被自动清理 | 恢复连接后仍有最近 7 天数据 |
| 硬件故障 | 网关容器停止 | 检查边缘服务器状态 |
| AuthKey 含非 ASCII 字符 | 日志 "含非 ASCII 字符" | 替换为纯英文/数字/符号密钥 |

## 场景 8: CI 流水线失败

**症状**：GitHub Actions 显示红色 ❌

**常见失败模式**：

| 阶段 | 失败原因 | 修复 |
|------|---------|------|
| dotnet restore | NuGet 源不可达 | 检查 `nuget.config` 或重跑 |
| dotnet build | TreatWarningsAsErrors | 修复新增 warning 或显式 suppress |
| Unit test | 断言失败 | 本地复现: `dotnet test tests/EquipAI.Tests.Unit` |
| Integration test | Testcontainers 超时 | CI 环境 Docker 性能问题，重跑 |
| tsc --noEmit | TypeScript 类型错误 | `npx tsc --noEmit` 本地修复 |
| ESLint | 新增 warning/error | `npx eslint src/` 本地修复 |
| vitest | 前端单测失败 | `npm run test` 本地复现 |
| Playwright E2E | 超时或元素找不到 | 查看 Artifacts 中的 HTML 报告 + 截图 |
| Trivy | HIGH/CRITICAL CVE | 升级基础镜像或相关依赖 |

**本地重跑 CI**：

```bash
# 后端
dotnet test tests/EquipAI.Tests.Unit
dotnet test tests/EquipAI.Tests.Integration

# 前端
cd frontend && npx tsc --noEmit && npx eslint src/ && npm run test && npm run build

# E2E (需本地有 PG + Redis)
# 见 .github/workflows/ci.yml 中 e2e job 的环境变量配置
```

## 场景 9: 前端白屏 / 加载失败

**症状**：浏览器访问显示白屏或 "加载中..." 卡住

**排查步骤**：

```bash
# 1. 打开浏览器 DevTools (F12) → Console
# 常见错误:
# - Failed to load module script (路径错误)
# - Uncaught SyntaxError (构建缓存问题)
# - Failed to fetch (API 不可达)

# 2. 检查 Nginx 配置
docker compose logs frontend --tail=20
# 确认 SSL 证书存在: docker exec equipai-frontend ls -la /etc/nginx/ssl/

# 3. 检查前端容器
curl -I https://localhost  # 返回 200
curl -I http://localhost:5173  # 开发服务器

# 4. 清除浏览器缓存或硬刷新 (Ctrl+Shift+R)

# 5. 检查后端 API 是否可达 (前端 Nginx 代理到后端)
curl http://backend:8080/health
```

**常见原因**：

| 原因 | 排查 | 修复 |
|------|------|------|
| API 不可达 | JS 控制台 404/502 | `docker compose restart backend` |
| SSL 证书缺失 | Nginx 日志 "cannot load certificate" | 按 [`docs/DEPLOY.md`](../DEPLOY.md) 预置 CA 签发的正式证书并重新执行生产校验；`generate-cert.sh` 仅限开发/测试 |
| Build 缓存 | JS 控制台 SyntaxError | `docker compose build --no-cache frontend` |
| PWA Service Worker 缓存旧代码 | Application → Service Workers → Unregister | `navigator.serviceWorker.getRegistrations()` |
| CORS 问题 | Console: "CORS" 错误 | 检查 FRONTEND_URL 配置 |
| Nginx 配置错误 | Nginx 日志 "invalid directive" | `nginx -t` 验证配置 |

## 场景 10: Redis 内存超限

**症状**：频繁的 OOM 或 Redis 响应变慢

**排查**：

```bash
# 1. 查看 Redis 内存使用
docker exec equipai-redis redis-cli -a $REDIS_PASSWORD INFO memory
# used_memory_human / maxmemory_human

# 2. 查看 key 分布
docker exec equipai-redis redis-cli -a $REDIS_PASSWORD --bigkeys

# 3. 查看 TTL 分布
docker exec equipai-redis redis-cli -a $REDIS_PASSWORD INFO keyspace

# 4. 查看当前最大 key
docker exec equipai-redis redis-cli -a $REDIS_PASSWORD \
  --eval <(echo 'return redis.call("MEMORY", "USAGE", KEYS[1])')
```

**常见大数据量 key**：

| key 模式 | 用途 | 增长 | 清理 |
|----------|------|------|------|
| `refresh:{userId}` | 刷新令牌 | 用户数 × 1 | 7 天 TTL 自动过期 |
| `refresh_token:{token}` | 反向索引 | 登录次数 | 7 天 TTL 自动过期 |
| `pwdreset:{token}` | 密码重置 | 30 分钟 TTL | 自动过期 |
| `mfa_challenge:{token}` | MFA 挑战 | 5 分钟 TTL | 自动过期 |

**解决**：

```bash
# 增加 maxmemory (docker-compose.yml)
redis:
  command: redis-server --maxmemory 512mb

# 主动清理过期 key
docker exec equipai-redis redis-cli -a $REDIS_PASSWORD MEMORY PURGE
```
